# Fastlane contributions and distributed rebases

Fastlane changes let an upstream StarRocks contribution enter the Celonis fork before it is available in the
upstream `branch-3.5-cc` branch. The tooling in `celonis/tools/fastlane_rebase.py` temporarily removes these changes
during an upstream rebase and distributes still-pending work to its responsible authors.

## Creating a fastlane PR

A fastlane PR into this repository must:

1. Target the repository's current default branch directly.
2. Contain exactly one commit.
3. Put the same marker in the PR title and commit subject, for example `[FASTLANE-77123]`.
4. Keep the normal title category first, for example `[BugFix] Fix decoded CTE refs [FASTLANE-77123]`.
5. Reference a real PR in `StarRocks/starrocks` whose base is `main` or `branch-3.5-cc`.

The upstream PR may be open or merged. A closed, unmerged upstream PR is rejected when the internal PR is opened.
The same upstream PR number cannot be used by multiple fastlane commits. PRs with `[FASTLANE-REBASE]` in the title
are generated by the distributed-rebase workflow and follow separate validation.

The `validate-fastlane-reference` check enforces these rules. After the workflow has been piloted, a repository
administrator must add its stable check name to the default-branch ruleset.

## Starting a rebase

Run **Fastlane Rebase and Test** with:

- `mode=start`
- an empty `run_id`

The workflow snapshots the current fork history, creates an upstream-aligned base and recovery branch, then rebases
the non-fastlane series. The snapshot and report are retained as a workflow artifact for 30 days.

If there are no pending fastlanes, the same workflow run executes presubmit, builds, compliance, and E2E tests and
opens the normal integration-rebase PR. No additional trigger is required.

If a normal rebase conflict occurs, the workflow summary prints exact recovery commands. Run them locally, resolve
the rebase with `git rebase --continue`, push the deterministic recovery branch with `--force-with-lease`, and invoke
the workflow again with `mode=continue` and the original start run ID.

## Restoring a pending fastlane

When pending work exists, the workflow opens a draft parent PR and one draft `[FASTLANE-REBASE]` PR per responsible
author. Each child PR contains a temporary `.fastlane-rebase/<run-id>/<author>.txt` file and repeats its restore
command in the PR description.

Run that command from a clean checkout. It downloads the immutable snapshot, cherry-picks assigned commits in order,
rebases them onto the latest central branch, removes the temporary bootstrap commit from history, and pushes with
`--force-with-lease`.

If cherry-picking stops on a conflict:

1. Resolve the files and run `git cherry-pick --continue` until the sequence finishes.
2. Rerun the restore command with `--finish --push`.

If the later rebase onto an updated central branch stops instead, finish it with `git rebase --continue`, then use
the exact `git push --force-with-lease` command printed by the tool.

Mark the PR ready after pushing. Child CI requires the branch to contain the current central SHA, then invokes the
normal presubmit workflow at the validated child head. When its current-base status is green, comment exactly
`/merge`. Any repository writer may issue the command. No approval is required.

The dedicated merge workflow rejects drafts, stale bases, stale checks, and invalid metadata. It rebase-merges the
exact checked head. After one child merges, every remaining child must rebase onto the updated central branch and pass
CI again.

## Finalization and recovery

The last successful child merge dispatches finalization automatically. Finalization verifies that every expected
fastlane remains a separate marked commit, then runs the full integration path and marks the parent PR ready. Retry a
failed finalization manually with `mode=finalize` and the original start run ID.

The central rebaser owns final integration failures and may push non-fastlane corrective commits directly to the
central branch before retrying. These extra commits are reported but not blocked.

Do not manually squash-merge child PRs. Finalization detects missing individual marker commits and stops, but repair
is intentionally handled case by case. The tooling also does not automate author reminders, semantic dependency
detection, repeated upstream references, or scheduled rebases.
